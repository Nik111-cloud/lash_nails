# Метрика: цели и офлайн-конверсии

Счётчик сайта: `113129252`. Настройки ниже сверены со скриншотом целей от 7 октября 2026 года. Изменения в кабинете выполняются отдельно; коммит меняет только сайт и эту инструкцию.

## Что добавлено на сайт

- `metrika-client.js` получает актуальный ClientID через `getClientID` при загрузке и после восстановления страницы из кеша браузера.
- ClientID сохраняется строкой в `localStorage.yandex_client_id`. Старое значение не используется вместо ответа счётчика. При ошибке/таймауте получения кеш очищается, если хранилище доступно.
- `window.getYandexClientID(callback)` также возвращает Promise. Для новой заявки использовать `await window.getYandexClientID()`, затем отправить ID вместе с заявкой на сервер. Отсутствие Метрики возвращает `null` через ограниченное время; звонки и переходы не блокируются.
- Когда ID получен, обе ссылки WhatsApp содержат заготовленное сообщение с полным ClientID как кодом обращения. Администратор должен перенести код из полученного сообщения в конкретную запись. Клиент может удалить текст или не отправить сообщение; клик не доказывает обращение.
- ID не добавляется в ссылку DIKIDI: обработка произвольного параметра сервисом не подтверждена. На сайте пока нет сервера/CRM для сохранения обращений.

## Что поправить в кабинете Метрики

| Текущая цель | Действие |
| --- | --- |
| `Успешная_Запись_Dikidi`, `order_confirmed` | Если цель должна получать штатное событие интеграции DIKIDI, заменить условие на **совпадает `book_completed`**. В настройках формы DIKIDI указать счётчик `113129252`. Если `order_confirmed` уже используется внешней системой, сохранить его и создать отдельную цель `book_completed`. |
| `Клиент_Пришел_На_Запись`, `pay_confirmed` | Уточнить смысл. Для факта посещения оставить имя и событие, передавать без дохода. Для оплаты создать отдельную цель **совпадает `offline_paid`** с фактической суммой. Если `pay_confirmed` уже означает оплату, переименовать текущую цель в «Клиент оплатил», а для посещения создать `offline_attended`. Не считать посещение доказательством оплаты. |
| `Состоявшийся_Звонок`, `call_confirmed` | Поставить **совпадает `call_confirmed`**. Отправлять только из коллтрекинга или подтверждённых данных администратора с реальным идентификатором посетителя. |
| `Запись_WhatsApp`, `order_whatsapp_confirmed` | Поставить **совпадает `order_whatsapp_confirmed`**. Передавать после подтверждения записи администратором с ClientID из обращения. |
| Все цели «Клик…», «В_Один_Клик_Dikidi» | Сохранить как измерение нажатий. Проверить привязку к актуальным кнопкам после изменений верстки; не интерпретировать «В один клик» как созданную запись. |
| Автоцели телефона и мессенджера | Можно оставить для проверки. Не суммировать с ручными целями кликов: одно действие может выполнить несколько целей. |

В `site.js` уже отправляются `booking_click`, `phone_click`, `whatsapp_click` с параметрами `placement`, `master_id`, `service`. На скриншоте соответствующие цели типа «Целевое событие» не видны. При необходимости создать их с условием «совпадает». Это дополнительные цели намерения; существующие цели «клик по кнопке» продолжат работать независимо. Код не вызывает `pay_confirmed`, `order_confirmed`, `call_confirmed`, `order_whatsapp_confirmed` при кликах.

Изменение условия существующей цели влияет на дальнейший сбор и не пересчитывает историю. Не удалять цели с накопленной статистикой без необходимости.

## Связь обращения с посещением

Хранить одну запись на посещение: `appointment_id`, `client_id` (текст), телефон, канал, время создания, услугу, мастера, статус, время оплаты и фактически полученную сумму. По возможности сохранять UTM и yclid при обращении. Повторные посещения имеют отдельные номера записей.

- WhatsApp: переносить код из реально полученного сообщения в запись клиента.
- Телефон: для автоматической связи нужен динамический коллтрекинг, передающий ClientID в CRM. Ссылка `tel:` не сообщает браузеру телефон звонящего или результат разговора.
- DIKIDI: проверить с поддержкой сохранение ClientID у записи, доступность его в экспорте/API и передачу изменений статуса/оплат. Интеграция целей сама по себе не подтверждает эти возможности.
- Формы на своём сайте: отправлять ClientID и телефон одной заявкой на сервер. Не хранить базу клиентов в публичных файлах сайта.

## Офлайн-загрузка

Для простого CSV создать цель типа «Целевое событие», условие «совпадает». `Target` — текстовый идентификатор события, а не числовой ID цели. Для новой цели оплаты использовать `offline_paid`.

```csv
ClientID,Target,DateTime,Price,Currency
1234567890123456789,offline_paid,1791288000,2500,RUB
```

Это условный пример, не готовый файл для загрузки. Заменить ID, время и сумму реальными значениями. UTF-8; DateTime — фактическое время события в Unix timestamp в секундах (не миллисекундах), не в будущем. Учитывать часовой пояс при преобразовании времени. ClientID хранить как текст, не округлять в Excel. Для посещения можно передавать только `ClientID,Target,DateTime`, без выручки.

Загрузить: Настройка → Загрузка данных → Загрузка офлайн-конверсий → привязка по ClientID. Проверить статус каждой строки в отчёте «Офлайн-конверсии»; обработка может занимать до трёх часов. Передавать ежедневно и хранить отметку экспорта по номеру записи + событию, чтобы не повторять одну оплату. Телефон не подставляется вместо ClientID в этом формате.

Период дополнения визитов — 21 день от последнего визита до обработки. Для заказов CRM, которые уже привязаны к визиту, предусмотрено изменение в пределах 111 дней от этого визита. При длинном сроке до оплаты предпочтительна своевременная отправка заказа CRM с последующим обновлением статуса. LocalStorage не продлевает окно атрибуции. OAuth-токен автоматической загрузки хранить на сервере.

## Проверка перед использованием целей в рекламе

1. Открыть сайт с тестовой UTM-меткой и `_ym_debug=2`; проверить клики по кнопкам. При фильтре «Не учитывать мои визиты» использовать приватный режим.
2. Проверить `await getYandexClientID()` и `localStorage.getItem('yandex_client_id')`: должны совпадать при работающем счётчике.
3. Проверить обе ссылки WhatsApp: текст содержит тот же ID; открыть сообщение и перенести код в тестовую запись.
4. Создать тестовую запись DIKIDI; проверить `book_completed` и источник перехода. Переход на другой домен требует проверки атрибуции, одного наличия события недостаточно.
5. Загрузить тестовую офлайн-конверсию с реальным ClientID и проверить её привязку.
6. Проверить сайт с заблокированной Метрикой и недоступным localStorage: переходы должны работать без ошибок.
